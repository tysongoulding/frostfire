## 3. MicroVM Network Isolation Invariant Audit

### 3.1 Invariant Definition
From `AGENTS.md` (lines 14-16) and `PROJECT.md` (lines 87-90):
- **MicroVM Isolation**: MicroVM instances run on isolated bridge networks (`172.16.x.0/24`). Never bridge unauthenticated guest networks to the public internet.
- **Firewall Invariant**: Forwarding of guest TAP packets to public WAN interface is FORBIDDEN. No `iptables -t nat -A POSTROUTING -o <WAN> -j MASQUERADE` for TAP subnets. MicroVM guest egress is strictly outbound-only via the reverse tunnel to `frostfire-gateway`.

### 3.2 Violation in `deploy/aws/firecracker-hypervisor.yaml`
Inspection of `deploy/aws/firecracker-hypervisor.yaml` lines 261–269 reveals:
```bash
261:           # 4. Configure Networking & Bridge for MicroVM Tap Interfaces
262:           mkdir -p /var/lib/frostfire /var/run/frostfire
263:           sysctl -w net.ipv4.ip_forward=1
264:           echo "net.ipv4.ip_forward = 1" >> /etc/sysctl.d/99-frostfire.conf
265: 
266:           # Setup bridge and NAT rule
267:           PRIMARY_IFACE=$(ip -4 route show default | awk '{print $5}' | head -n1)
268:           iptables -t nat -A POSTROUTING -o "${PRIMARY_IFACE}" -j MASQUERADE || true
```

#### Why This Violates Security Invariants:
1. **Unrestricted Guest Egress**: Enabling `net.ipv4.ip_forward=1` combined with an unconditional `POSTROUTING MASQUERADE` on `${PRIMARY_IFACE}` allows any IP packet originating from an unauthenticated guest microVM (e.g. `172.16.x.2`) to be masqueraded as host WAN traffic and routed directly out to the public internet.
2. **Reverse Tunnel Bypass**: The Frostfire security architecture relies on all outbound communication traversing the hardened `frostfire-gateway` via `AgentTunnelService.OpenTunnel` with constant-time token authentication. Direct NAT masquerade completely circumvents this control plane, allowing rogue or compromised guest processes to bypass tenant gating, exfiltrate data, or initiate external network attacks.
3. **AWS IMDS Metadata Exposure**: By default, an unrestricted forwarder allows guest microVMs to query the AWS link-local Instance Metadata Service at `169.254.169.254`, risking exposure of instance profile IAM credentials to guest code.
4. **Missing TAP Interface Initialization**: While line 268 adds a masquerade rule, the template completely omits the setup of the TAP interfaces (`tap0`, `tap1`, `tap2`) and their IP addresses (`172.16.x.1/24`) required by `run-vm.sh`.

## 4. Remediation: Isolated Bridge Implementation

To eliminate the security invariant violation, the UserData section of `firecracker-hypervisor.yaml` must be updated to enforce strict network isolation:
1. **Delete** the unconditional `iptables -t nat -A POSTROUTING -o "${PRIMARY_IFACE}" -j MASQUERADE` rule.
2. **Preconfigure point-to-point TAP interfaces** (`tap0` -> `172.16.0.1/24`, `tap1` -> `172.16.1.1/24`, `tap2` -> `172.16.2.1/24`).
3. **Explicitly DROP all packet forwarding** from guest subnet `172.16.0.0/16` to the WAN interface `${PRIMARY_IFACE}`.
4. **Block access to AWS IMDS** (`169.254.169.254`) from guest subnets.
5. **Permit only local point-to-point communication** between guest (`172.16.x.2`) and host (`172.16.x.1`) to enable in-VM agents to connect to the reverse-tunnel gateway.

+          setup_tap() {
+            local TAP_NAME="$1"
+            local HOST_IP="$2"
+            if ! ip link show "${TAP_NAME}" > /dev/null 2>&1; then
+              ip tuntap add dev "${TAP_NAME}" mode tap user root

+            fi
+          }

+          setup_tap "tap0" "172.16.0.1"
+          setup_tap "tap1" "172.16.1.1"
+          setup_tap "tap2" "172.16.2.1"

+          # 1. Zero NAT MASQUERADE on WAN interface for microVM TAP traffic.
+          # 2. Explicitly DROP all forwarding from microVM guest subnets (172.16.0.0/16) to WAN.

+          iptables -A FORWARD -s 172.16.0.0/16 -d 169.254.169.254 -j DROP

+          for TAP in tap0 tap1 tap2; do

+            iptables -A OUTPUT -o "${TAP}" -d 172.16.0.0/16 -j ACCEPT
+          done

## 5. Architectural Review of Individual Templates

### 5.1 `cloudformation.yaml` (ECS Fargate + NLB gRPC Ingress)
- **L4 NLB Pass-Through**: The Network Load Balancer operates at Layer 4 (TCP), listening on port 50051 and forwarding directly to the Fargate task IP on port 50051. This preserves HTTP/2 gRPC streaming semantics and TLS 1.3 encryption end-to-end between client and container without ALB layer-7 termination interference.
- **Fargate Task Scaling**: DesiredCount is set to 1. In `frostfire-gateway`, session state is maintained in an in-memory `SessionRegistry`. If scaled beyond 1 task, an external shared state store (or client affinity) would be required; for current architecture, 1 task with horizontal expansion managed via DNS routing matches the design.
- **Tenant Token Parameterization**: The container definition executes `["frostfire-gateway", "--bind", "0.0.0.0:50051"]`. Since `frostfire-gateway` reads `FROSTFIRE_TENANT_TOKEN` from the environment or `--tenant-token` argument, adding an optional `Environment` block in `TaskDefinition` enables configuring tenant tokens via CloudFormation parameters or AWS Secrets Manager.

### 5.2 `firecracker-hypervisor.yaml` (Bare-Metal Hypervisor & WebRTC)
- **Bare-Metal KVM Compute**: Correctly restricts `InstanceType` parameter to `.metal` families (`c6i.metal`, `c7i.metal`, `m6i.metal`, `c5.metal`, `m5.metal`), which provide unvirtualized `/dev/kvm` hardware access required by Firecracker.
- **WebRTC STUN/TURN Integration**: Declares an AWS Kinesis Video Streams Signaling Channel (`AWS::KinesisVideo::SignalingChannel`) and provisions `/usr/local/bin/get-aws-ice-servers.sh` on the host to fetch dynamic STUN and TURN credentials via AWS CLI.
- **Port Layout**: Correctly exposes the port matrix:
  - `50051/tcp`: gRPC Edge Gateway
  - `6080/tcp`: Primary user noVNC display (:1)
  - `6081/tcp`: Token-multiplexed websockify for fork displays (:2, :3, etc.)
  - `8444/tcp`: KasmVNC WebRTC HTTPS interface
  - `3478/udp`, `3478/tcp`: STUN/TURN fallback
  - `49152-65535/udp`: Dynamic WebRTC media packets

### 5.3 `poc-3user.yaml` (Lean Single-Host POC)
- **Scope & Limitations**:
  - Operates as a shared Ubuntu OS host using Xvfb displays (:1, :2, :3) rather than isolated Firecracker microVMs.
  - Exposes port 3000 running `frostfire-exec-server.py` with an unauthenticated `/exec` endpoint.
  - `AllowedCIDR` defaults to `0.0.0.0/0`. While marked in description as "Restrict to your IP in production", in an open deployment anyone could execute arbitrary commands under user `ubuntu`.
  - **Recommendation**: For production, use `firecracker-hypervisor.yaml` and `cloudformation.yaml`; retain `poc-3user.yaml` strictly as a lightweight local development / low-cost test fixture.
